# Критерии ревью

Этот файл — источник истины для проверки пул-реквестов в проекте «Календарь звонков».
Автоматический ревьюер получает его содержимое из базовой ветки и обязан оценивать
изменения именно по этим критериям. Человек-ревьюер использует тот же список.

Ревью независимое: автор изменения не считается экспертом по собственному PR, а
авторевью не блокирует merge. Итог авторевью — комментарий к PR и необязательный
check `OpenCode review`.

## Как оценивать

- **Блокирующее** — нарушен инвариант домена, контракт API, безопасность или
  потеря данных. Без исправления PR не стоит мержить.
- **Некритичное** — риск, неоднозначность, недостающий тест или UX-проблема.
  Можно вынести в отдельную задачу.
- Не повторяй замечания линтеров и форматтеров: их ловят `mise run check` и CI.
- Каждое замечание должно ссылаться на критерий ниже и на место в коде
  (`file:line`), а не быть общим пожеланием.
- Если блокирующих замечаний нет, так и напиши.

## Домен календаря

Проверяй поведение, а не только названия. Термины и их смысл — в `GLOSSARY.md`,
принятые решения — в `docs/adr/`.

### Термины

- В коде, API и БД используются `MeetingType` («Тип встречи»), `Slot` («Слот») и
  `Booking` («Бронь»). Слово «событие» не должно возвращаться как доменный термин
  или имя сущности.
- «Заявка» — это бронь в статусе `pending`, а не отдельная сущность.
- «Живая бронь» — `pending` или `confirmed`; `declined` живой не считается.

### Занятость слотов

- Слот занят, если его время пересекается с **любой** живой бронью, независимо от
  типа встречи: владелец один и не может вести две встречи одновременно.
- Длительность слота равна длительности типа встречи; проверка пересечения
  учитывает длительность, а не только время начала.
- `declined` не занимает слот: на освободившееся время можно записаться снова.
- Границы интервалов должны быть согласованы: соседние слоты не считаются
  пересекающимися, а частичное наложение — считается.
- Прошедшие слоты не предлагаются для записи и не принимаются API.
- Часовые пояса не должны «плыть»: хранение и сравнение времени согласованы,
  переход на летнее/зимнее время не создаёт двойных или потерянных слотов.

### Статусы и переходы

- Новая бронь создаётся только как `pending` и удерживает слот.
- Владелец переводит заявку только из `pending` в `confirmed` или `declined`;
  других переходов нет, решение окончательное.
- Согласование обязательно для всех типов встреч, а не включается флагом.
- Существующие брони при миграции становятся `confirmed`; массового превращения
  подтверждённых броней в заявки быть не должно.

### Инварианты гостя

- У гостя не больше одной живой брони на один тип встречи.
- Живые брони гостя не пересекаются по времени между разными типами встреч.
- Уникальность пары «тип встречи + начало» обеспечивается на уровне БД для
  `pending` и `confirmed`; для `declined` ограничение не действует.
- Создание брони атомарно: две одновременные заявки на один слот не должны обе
  завершиться успехом. Конфликт возвращает понятную ошибку, а не 500.

### Права и владелец

- В сервисе один предопределённый владелец и **нет аутентификации by design**.
  Добавление логина, регистрации или ролей — изменение продукта, а не рефакторинг.
- Подтверждать и отклонять заявки может только владелец; гость не может менять
  статус брони.
- Удаление типа встречи не должно молча терять живые брони: проверь каскады,
  ограничения и поведение API.

## Контракт API

- `api/*.tsp` — источник истины. `api/openapi/openapi.yaml`,
  `frontend/src/api/schema.d.ts` и `backend/app/schemas/contract.py` генерируются;
  руками их править нельзя.
- Если менялся `.tsp`, в PR должен быть результат `mise run api:generate`, а
  `mise run api:check` — проходить.
- Маршруты, коды ответов, тела запросов и ответов должны совпадать с OpenAPI.
  `backend/tests/test_contract.py` не должен обходить проверку.
- Новые поля и статусы должны быть описаны в контракте, а не только в коде.
- Ошибки API должны быть предсказуемыми и не раскрывать внутренние детали.

## Backend и данные

- Код типизирован, проходит ruff и mypy; настройки читаются через
  `app.core.config.get_settings()`.
- Работа с БД идёт через асинхронный SQLAlchemy; транзакции не оставляют
  частично записанных броней.
- Миграции Alembic применимы с нуля и к существующей базе; внешние ключи и
  уникальные индексы включены.
- `FAKE_NOW` используется только в тестах и не влияет на продовое поведение.
- Нет SQL-инъекций, утечек секретов, отладочных print и широких прав.

## Frontend и UX

- Интерфейс использует термины и статусы из `GLOSSARY.md`; «Ожидает
  подтверждения», «Подтверждена» и «Отклонена» не смешиваются.
- Заявка визуально отличается от подтверждённой встречи, а после решения владельца
  гость видит окончательный статус.
- Обработаны загрузка, пустое состояние и ошибка сети; пользователь не видит
  сырой текст исключения.
- Типы берутся из сгенерированной схемы; `any` и обход типов не скрывают
  несоответствие контракту.
- Затронутые сценарии покрыты тестами Vitest; сетевые вызовы в тестах
  перехватываются MSW, а не реальным backend.
- Клавиатурная навигация, подписи полей и контраст не ухудшены.

## Тесты и проверки

PR не готов, если не проходит `mise run check`. Отдельно проверь:

- тесты на новое поведение и на граничные случаи домена: пересечения, статусы,
  повторная запись после `declined`, одновременные заявки;
- `api:check` и `actions:lint`, если менялись контракт или workflow;
- `e2e`, если затронут пользовательский сценарий записи или решения владельца;
- отсутствие регрессий в существующих тестах, а не только зелёный новый тест.

## Гигиена PR

- PR ссылается на задачу (`Closes #N`) и заполняет шаблон: проверки, риск,
  способ отката.
- Заголовок PR — Conventional Commit; в диффе нет случайных файлов, секретов,
  закомментированного кода и отладочных логов.
- Риск и откат описаны честно: миграции, изменения контракта и поведение
  пользователей отмечены отдельно.

## Формат отчёта авторевью

1. Краткое резюме: что меняется и насколько это рискованно.
2. **Блокирующие замечания** — по одному пункту на находку: критерий, `file:line`,
   проблема, чем это грозит, как исправить.
3. **Некритичные замечания** — то же, но с пометкой, что можно вынести отдельно.
4. **Что проверено** — короткий список критериев, по которым замечаний нет.
5. Если замечаний нет: «Блокирующих замечаний нет».

Не выставляй approve или request changes: авторевью оставляет только комментарий,
а решение о merge принимает человек.
